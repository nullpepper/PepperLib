# PersistentStore 提取记录

> 日期：2026-08-25。版本：PepperLib 0.8.0（Experimental）。

## 提取依据（纪律）

双消费者共设计（规格一致、代码未先存在）：

- **PVP 竞技场**（pepper-plugins/PepperPvpArena）：地图/模板配置、比赛结果与
  战绩持久化——需要「全量小数据、启动即加载、修改异步写盘」的文件型 KV；
- **漂流瓶插件**（规划中）：类似持久化需求（用户确认）。

与既有 `ltd.pepper.lib.storage`（SQL 迁移框架）的关系：不同范式——
SQL 适合结构化查询（战绩统计/排行榜）；文件 KV 适合全量小数据简单读写
（配置/存档）。按需选择，不冲突。

## 设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 加载语义 | 构造时全量加载；损坏 → IOException 构造失败 | 启动即暴露数据问题，不静默空表丢数据 |
| 写盘 | 修改异步（executor 注入）+ 写中合并 + 单飞 | 不卡调用线程；突发修改合并为一次写 |
| 原子性 | 临时文件 + 原子 rename | 崩溃/断电无中间态（旧文件完好或新文件完整） |
| 兜底 | flush() 同步落盘（关闭/检查点） | 异步写失败不静默丢最后一批修改 |
| 失败策略 | 异步失败保留 dirty + 日志；flush 抛 IOException | 下次修改重试；同步路径失败可见 |
| 序列化 | StoreCodec 接口注入 | PepperLib 纯 JDK 零依赖纪律 |
| 延迟窗口 | v1 不做（单飞合并足够） | 性能优化列为后续（writeDelayMillis） |

## 竞态安全论证（单飞合并）

每次修改后：要么本次写快照包含该修改，要么已排后续写任务——
`put` 先更新 table 再置 dirty + scheduleWrite；写任务锁内重置 writeScheduled、
取 dirty 快照，锁外写盘；写盘期间的新修改触发下一次写（合并）。
唯一丢数据窗口 = 进程在写盘完成前崩溃（异步本质），flush() 兜底。
